I built [[https://github.com/travisjeffery/tidewaiter][Tidewaiter]], a package firewall. Package managers point at it instead of the public registry. It checks each package version against local policy and OSV before download, caches approved artifacts, and says why when it blocks one. At [[https://oscilar.com][Oscilar]] it was called Package Firewall; a tidewaiter was the customs officer who inspected cargo before it landed.

A lockfile pins a version. It does not say if that version is safe. A phished maintainer can publish a bad version, a typosquat sits one keystroke from a real package, and an install script runs on a laptop with cloud credentials. Most teams have nothing between the package manager and the registry.

Commercial products do this well. Oscilar wanted the same basic checks in its own infrastructure. AI let me build them in weeks instead of quarters.

** The risk

The attacks are boring and they work:

- *Compromised maintainers.* An attacker gets publish access and ships a malicious patch release. Everyone with a caret range pulls it on their next install. In September 2025, phished maintainer credentials put malicious versions of =chalk=, =debug= and more than a dozen other packages on npm, with over two billion weekly downloads between them, and the Shai-Hulud worm spread itself through stolen npm tokens the same month.
- *Typosquats.* =lodahs= instead of =lodash=. One typo, and the package runs.
- *Install scripts.* npm lifecycle scripts, Python build backends and Gradle plugins all run code at install or build time, before any test or review sees it.
- *Known vulnerabilities.* Less dramatic and far more common. A critical CVE in a transitive dependency ships because nobody looked.

All four hit at download time, on developer machines and CI runners. A later scan is too late for a machine that already ran the code.

** What the products give you

[[https://socket.dev][Socket]] analyzes packages for malware and risky behavior as well as CVEs. Its [[https://docs.socket.dev/docs/socket-firewall-overview][Socket Firewall]] is "an HTTP/HTTPS proxy server that sits between package managers and package registries" and checks each request against Socket's data before it reaches the registry. It blocks confirmed malware, and the enterprise version adds a registry mode that package managers point at directly.

[[https://jfrog.com][JFrog]] comes at it from the repository manager. Artifactory remote repositories proxy and cache public registries. [[https://docs.jfrog.com/security/docs/curation-intro][JFrog Curation]] enforces security and license policies "before they're even used", at the point a package enters a remote repository, with conditions for malicious packages, critical CVEs, licenses and package maturity. Xray handles gating for what's already in local repositories.

Both do four things:

1. *One door.* Package managers fetch from a proxy you control instead of the public registries.
2. *A decision before download.* The proxy checks each package version against threat data and your policy before bytes reach a machine.
3. *A cache.* The proxy serves approved artifacts from your own storage: faster, and still up when the registry is slow or down.
4. *An explanation.* A developer whose install fails can find out why, and what to do next.

If you need deep malware analysis, license policy across dozens of ecosystems, or a full repository manager, buy one of these. Oscilar needed those four things for four ecosystems, inside infrastructure it already runs.

** Building it with AI

Each ecosystem has its own URL layout, metadata format and client quirks. A cache for untrusted bytes takes care to get right.

Agents now write most of the code. I set the behavior and constraints, review the diffs, and make the decisions. The [[https://github.com/travisjeffery/tidewaiter/commits/main][history]] runs from the first commit in late June to the explain-blocks release in November, almost all of it through pull requests, with unit tests on the decision and cache paths and [[https://github.com/travisjeffery/tidewaiter/blob/main/scripts/live-smoke.sh][live smoke tests]] against the real registries.

AI got it wrong at first. Some bugs it shipped and then fixed:

- OSV reports severity as a CVSS vector string, not a number. The first parser read a number off the end of the vector, every severity came out as zero, and the block threshold never fired. The [[https://github.com/travisjeffery/tidewaiter/blob/main/internal/intel/severity_test.go][regression test]] now feeds it real vectors.
- pip and uv ask for gzip. A compressed metadata response can't be rewritten byte for byte, so pip and uv downloaded every wheel straight from =files.pythonhosted.org=, around the firewall. I changed it to always fetch metadata uncompressed.
- npm packuments can pass 28 MB. A 20 MiB read cap cut them off mid-string and served the stub as a complete response. I made the rewrite stream.

Each bug passed unit tests with tidy fixtures and failed on real traffic. So I made real traffic part of the tests.

** How it works

Tidewaiter is a Go service. Package managers point at it as their registry:

#+begin_src bash
npm config set registry http://localhost:8080/npm/
pip config set global.index-url http://localhost:8080/pypi/simple
export GOPROXY=http://localhost:8080/go
#+end_src

Maven and Gradle use it as a mirror. It does not intercept TLS: it only sees traffic pointed at it, and no machine needs a custom CA.

It supports npm-compatible registries (so npm, pnpm and Yarn), PyPI's Simple API (pip and uv), the Maven repository layout (Maven and Gradle), and the Go module proxy protocol. A =static= ecosystem covers fixed build assets, like Gradle distributions, that have no package coordinate and are pinned by checksum instead.

Every request goes through the same steps.

*** 1. Identify the package

Each route has an ecosystem adapter that turns a URL into a package and version, written as a [[https://github.com/package-url/purl-spec][purl]]: =/npm/shell-quote/-/shell-quote-1.9.0.tgz= becomes =pkg:npm/shell-quote@1.9.0=. Metadata requests (the npm packument, the PyPI index page) don't name a version and pass through to the next step without a vulnerability check. When the adapter can't identify an artifact, the request is unknown, and the config decides whether unknown means warn or block.

*** 2. Apply local policy

Policy files are purl globs:

#+begin_src yaml
deny:
  - "pkg:npm/lodahs@*"
warn:
  - "pkg:pypi/django@5.*"
allow:
  - "pkg:golang/golang.org/x/mod@v0.30.0"
#+end_src

Deny always wins, so a broad allow can't mask an explicit deny. An allow rule naming an exact version skips the threat check, which is how you take an exception for a package you've reviewed. Warn rules and wildcard allows still block malware, since a wildcard would also exempt the next, possibly compromised, release.

*** 3. Check threat data

Tidewaiter looks up anything policy didn't decide in [[https://osv.dev][OSV]], which aggregates the GitHub advisory database, the ecosystems' own advisories, and the OpenSSF malicious-packages feed (published under =MAL-= IDs). Findings at or above a CVSS threshold block; findings below it get the default action, warn in the example config. Tidewaiter caches results for a few hours, and if OSV is unreachable you choose whether to fail open or closed.

OSV is weaker than the products' data. It knows published advisories and reported malware. It does not look inside packages. I took that limit because the data is open, and Oscilar needed to own the firewall.

Writing this post turned up two more gaps. OSV's =MAL-= records, and GitHub advisories tagged CWE-506 (embedded malicious code), usually carry no CVSS score. A known-malicious package scored zero and fell through to the default action, so with =warn= Tidewaiter served it with a warning. And the optional release cooldown, which holds any version published less than =min_age= ago, never fired, because nothing looked up when a version was published. I fixed both. Malware now always blocks, whatever the threshold, the default action or a matching =warn= rule says, and a malicious result outlives the OSV cache so an OSV outage can't serve a package already seen to be malicious. In production, =flatmap-stream@0.1.1= (the payload behind the 2018 =event-stream= compromise) and =coa@2.0.3= (hijacked in 2021) now get a =403=. The cooldown looks up publish times from each registry: the npm packument, PyPI's upload time for the requested file, the Go proxy's =.info=, and Maven's =Last-Modified=.

*** 4. Explain the decision

A block is a =403= with the reason, written for the person whose install just failed:

#+begin_src text
Blocked by Tidewaiter: shell-quote@1.9.0 has GHSA-pqg4-j6r4-53mv (CVE-2026-102422),
severity 9.2 >= threshold 9.0: shell-quote: `quote()` command injection ... Affected: >=1.8.4,
<1.11.0. Fixed in 1.11.0; upgrade to a fixed version (update the lockfile, or override the
transitive dependency). Details: https://osv.dev/vulnerability/GHSA-pqg4-j6r4-53mv.
Request ID: 1234567890123456789. Exceptions: <decision.exceptions_url>
#+end_src

Each kind of block has its own next step. A vulnerability says which version fixes it. Malware says to remove it and treat the machine as compromised. A deny rule says to pick something else or ask for an exception, and every message links to wherever your team takes exceptions.

Only npm prints a =403= body. pnpm, Yarn, pip, uv, Maven and Gradle print the status and the URL and nothing else. So Tidewaiter also puts the explanation in =X-Package-Firewall-*= headers, and serves an =/explain= endpoint that takes the URL from the error, or a purl, and re-runs the same decision without downloading anything:

#+begin_src bash
curl -fsS --netrc -G https://packages.example.com/explain \
  --data-urlencode "url=https://packages.example.com/npm/shell-quote/-/shell-quote-1.9.0.tgz" \
  --data-urlencode format=text
#+end_src

A CI job can call it for every failed URL in its log. If a firewall blocks without a reason, developers go around it. If it names the advisory and the fixed version, they update the lockfile.

*** 5. Rewrite metadata so nothing goes around it

A proxy only protects you if every download goes through it. Registry metadata names where to download from: an npm packument lists tarball URLs on =registry.npmjs.org=, and a PyPI index page links wheels on =files.pythonhosted.org=. A client that follows those links fetches the artifact directly, skipping the firewall without anyone noticing.

So Tidewaiter rewrites metadata responses to point back at itself, as a stream, so a 28 MB packument never sits in memory.

*** 6. Serve from the cache

Tidewaiter caches approved artifacts on the local filesystem or in S3. The cache is deliberately much narrower than a general HTTP cache:

- The decision runs before every cache lookup, so a package blocked today can't be served from yesterday's cache entry.
- It caches only exact artifacts with a concrete name and version, and only clean responses: a =200=, no ranges, no conditional requests, no cookies, nothing marked =private= or =no-store=.
- It stages a hit to local disk and checks its recorded length and SHA-256 before a byte goes to the client. A missing, truncated or corrupt entry is just a miss.
- Public npm artifacts respect the registry's freshness headers, and an expired entry means a new fetch, never a stale fallback.

With several replicas, a DynamoDB lease makes sure a cold artifact is fetched from upstream once, not once per pod, and an upstream that answers =429= cools down every replica at once. That matters the first time a few hundred CI jobs hit an empty cache together. The [[https://github.com/travisjeffery/tidewaiter/tree/main/deploy/opentofu/modules][OpenTofu modules]] create the S3 bucket and DynamoDB table with least-privilege IAM policies.

For Gradle there's =tidewaiter prewarm=, which reads the committed lockfiles and verification metadata, downloads every artifact through the firewall checking each SHA-256, then does it again and fails unless every artifact is a cache hit the second time. Run it as one controlled job before a burst of CI traffic: a miss on the second pass means the cache isn't working.

** Limits

Tidewaiter acts on OSV and your policy. It does not look at package code or intercept TLS. It does not host your own packages, and it has no Artifactory or Nexus discovery. It covers four ecosystems.

At Oscilar it sits in front of CI in about twenty repositories. In the 30 days to November 3 it answered about 119 million requests and blocked 1,162 downloads of 27 distinct package versions. Of the 35 million artifact downloads eligible for the cache, 89.6% were served from it: 99.5% or better for npm, PyPI and Go, and 84.5% for Maven Central.

Tidewaiter is on GitHub at [[https://github.com/travisjeffery/tidewaiter][travisjeffery/tidewaiter]] under the Apache 2.0 license. The README has a quick start that runs it locally against the public registries.
